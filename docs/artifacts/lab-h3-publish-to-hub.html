Part 1

Export the table

5 min
1.1

Click it

/admin → Export to Parquet. Watch the runtime log.

1.2

Understand what it did — it is not what people expect

It ran a Spark read of the current snapshot and wrote fresh Parquet. It did not copy the files out of the warehouse bucket.

Why not just copy?

The warehouse already holds Parquet, so copying would be fewer steps. But those files are not the table. Iceberg keeps superseded files alongside current ones until snapshots expire, so after a compaction or an overwrite a raw copy silently republishes rows the table no longer contains. Reading through the table resolves the current snapshot's manifest.

1.3

Look at what it produced

in your lakehouse bucket, under app/export/uk-price-paid/ 
README.md                     <- dataset card, with the frontmatter the Viewer reads
data/part-00000-….parquet     <- the Parquet, in a data/ subdirectory
data/part-00001-….parquet

The data/ subdirectory is deliberate: pandas and pyarrow refuse a directory that mixes Parquet with anything else, so the card cannot sit beside them.

Part 2

Publish it with a Job

10 min
2.1

What a Job is

A container Hugging Face runs on its own hardware, once, then throws away. You give it a script, a hardware size, and any volumes to mount. It is not a Space: nothing is served, there is no URL — it runs to completion and exits.

Why that matters here, concretely

The export is tens of megabytes, and there are twenty-five of you. A Job mounts the same bucket the Space writes to and moves the bytes inside Hugging Face — nothing crosses the venue wifi.

2.2

Run it

hf jobs uv run scripts/publish-dataset.py \
  -v hf://buckets/<you>/lakehouse:/mnt/lakehouse \
  -e DATASET_REPO=<you>/uk-price-paid \
  -e PRIVATE=0 \
  -s HF_TOKEN \
  --flavor cpu-basic
FlagWhat it does
uv run <script>uploads your local script and runs it with uv, installing the dependencies declared in its header
-v hf://buckets/…mounts your bucket into the Job at that path
-e KEY=valuean environment variable the script reads
-s HF_TOKENpasses your token as a secret — not printed, not in the Job's logs
--flavor cpu-basicthe smallest hardware. This is a file copy; it needs nothing more

Not /data. Jobs reserves that path for its own artifacts when running a local script, and refuses the mount outright.

2.3

Why PRIVATE=0 — think before you run it

The script defaults to a private dataset. Public is what you want here, for a reason worth knowing:

The Viewer does not work on private datasets for free accounts

You get "Not supported: … Private datasets are only supported for PRO users and Enterprise Hub organizations." Publish private and Part 3 simply will not happen.

Public is also right for this data: UK Land Registry Price Paid, already public under the Open Government Licence, and the card the exporter wrote says so. That would not be true of your own company's data — which is exactly the judgement this flag is asking you to make.

2.4

Re-running is safe

The script skips the commit when nothing changed, so a second run reports "No files have been modified since last commit" rather than making an empty one.

Part 3

The Dataset Viewer

5 min
3.1

Open it

https://huggingface.co/datasets/<you>/uk-price-paid

Give it a minute after the Job finishes — the Hub indexes the Parquet in the background.

3.2

What you get, without configuring anything

Browsable tablepaginated, sortable, column types inferred
Column statisticsdistributions, null counts, min/max
SQL consoleDuckDB, running in your browser, against the Parquet
API endpointauto-generated, for rows and search
3.3

Why it works — there is no magic

The README.md the exporter wrote carries this frontmatter:

configs:
  - config_name: default
    data_files: "data/*.parquet"

That is the whole contract. The Viewer reads it, finds the Parquet, indexes it. Publish Parquet without a card and you get nothing.

3.4

Use the SQL console

SELECT town, COUNT(*) AS sales, ROUND(AVG(price)) AS avg_price
FROM train
GROUP BY town
ORDER BY sales DESC
LIMIT 20;

No install, no credentials, no cluster.

Part 4

The honest experiment

5 min
4.1

Same question, three engines — time each

EngineHow
Spark + Icebergyour app's Run Query
DuckDB in the browserthe Viewer's SQL console
DuckDB locallyhf datasets sql "SELECT … FROM 'hf://datasets/<you>/uk-price-paid/data/*.parquet'"

hf datasets sql needs DuckDB installed (brew install duckdb, or pip install duckdb). Without it, the browser console makes the point just as well.

4.2

The crossover is the lesson

For one year on one machine, DuckDB will very likely win — and saying so out loud buys enormous credibility, because the room already suspects it. Spark's case is the eleven-year load, the multi-node future, and Iceberg's snapshots and schema evolution. It is not the single-node scan.
