Model bake-off

Six models, six providers, one token — and an eval set that turns "which model is best" from an opinion into a measurement.

Before you start — you need F1 finished

This lab compares models using your eval set. You need at least three questions in scripts/questions.csv with expected answers you derived yourself. Without them there is nothing to compare, and every model will look identical.

There is no code to write. The model is already a runtime setting — the Model Picker at the bottom of /admin changes it per request. A bake-off costs no deploys at all, which matters: at roughly 90 seconds a deploy, doing this the obvious way would eat the whole hour.

// AiService, already in the code you cloned
String model = modelStore.get();          // whatever /admin is set to
OpenAiChatOptions.Builder perRequest = OpenAiChatOptions.builder().model(model);

2.3

What the 1B model does, and why it matters

You should get this:

model:     google/gemma-3-1b-it:featherless-ai
id    generated ran     correct   ms
q01   no        no      no        6000

Zero on the very first gate. Not "wrong answers" — nothing usable came back at all. The system prompt asks for JSON; this model replies with something else, so AiService refuses to guess and the endpoint returns an error rather than a query.

This is F1's structured output doing its job

A model that cannot follow the output contract fails loudly and early, instead of returning prose that gets executed as SQL. Try the same question in the app itself and read what comes back — the page shows you the raw reply rather than hiding it.

2.4

Look at the latency column too

Small does not mean fast. The 1B model was slower than the default in our run — the provider matters as much as the parameter count.

Part 3

Two settings that change the answer

10 min

Both live in src/main/resources/application.properties. Changing these is a deploy — edit, commit, git push hf main, wait for the build. Do one, not both, and compare against your baseline.

3.1

Thinking

src/main/resources/application.properties · line 40 
app.ai.reasoning-effort=none

The file records 21.7 s with thinking versus 1.2 s without, measured on Qwen/Qwen3.6-27B. Set it to low and re-run. Does accuracy improve enough to pay for that? Measure it.

Use app.ai.reasoning-effort, not the Spring one

The comment above that line explains why. Anything set on spring.ai.openai.chat.reasoning-effort becomes a client default, and runtime options merge over defaults rather than replacing them — so it can never be not sent. That breaks portability: none is fine on ovhcloud and returns 400: must be one of low, medium, or high on groq. AiService sends it per request and retries without it if a provider objects.

3.2

Temperature

src/main/resources/application.properties · line 56 
spring.ai.openai.chat.temperature=0.0

Raise it to 0.8, push, and run the harness twice without changing anything else. Watch reproducibility fall apart.

This is the concrete version of the question F1 left you with: how many runs before you would believe a change had helped?

Part 4

Decide, and say why

5 min
4.1

Answer these in writing

From your table
  1. Which model would you ship, and what did you trade away to pick it?
  2. Was the biggest model the best? It usually is not, for sixteen columns of text-to-SQL.
  3. What would change your mind — more questions, harder questions, more runs?

Then pool the room's tables. Attendees who wrote different questions will disagree about which model wins, and that disagreement is the lesson: your eval set defines "best", and it is only ever as good as the questions in it.
