Lakehouse Lab Catalogue

Twelve build-a-feature labs to swap into the optional slot, run as a second session, or hand out as take-home work. Every one of them ships a diff, not a screenshot.

Two things in the repo make this cheaper than it looks

  • images/kafka_connect/Dockerfile already installs iceberg/iceberg-kafka-connect:1.9.2, and compose.kafka.yaml already brings up a broker, Schema Registry, Connect and a Redpanda console. The streaming lab is configuration, not plumbing.
  • compose.yaml already runs Trino on :9999 against the same LakeKeeper catalog with vended credentials. The multi-engine lab is a JDBC URL.

What unlocks what

The core workshop's F1 is not just a lab, it's a dependency. Four of these bonus labs are scored with the same ten questions — which is what turns each of them from a demo into a result.

Track A

Iceberg internals

P1Time travel and a snapshot diff view

45 minmediumSpace lane

Build a /history page listing every snapshot, and a query page that can run against any of them. Iceberg's metadata tables are just SQL, which makes this far less work than it sounds:

SELECT * FROM lakekeeper.housing.staging_prices.snapshots;
SELECT * FROM lakekeeper.housing.staging_prices.files;

SELECT town, avg(price) FROM lakekeeper.housing.staging_prices
  VERSION AS OF 7834659812345678901 GROUP BY town;

The payoff is that everyone double-loads 2015 — load() appends — and then fixes it in one statement instead of reloading:

CALL lakekeeper.system.rollback_to_snapshot('housing.staging_prices', <snapshot_id>);

Concepts

Snapshot isolation; metadata tables as a first-class API; why “undo” is cheap in a table format and terrifying in a warehouse.

P2Write–audit–publish with branches showstopper

50 minhardSpace lane

Build ingestion that cannot publish bad data, using branches as a staging area that costs nothing. Change load() to write into a branch, audit it, and only then fast-forward main:

ALTER TABLE lakekeeper.housing.staging_prices CREATE BRANCH ingest_2016;
-- write with spark.wap.branch=ingest_2016, then assert:
--   no null transaction_id · price > 0 · dates inside the year
--   row count within ±20% of last year · record_status in (A,C,D)
CALL lakekeeper.system.fast_forward('housing.staging_prices','main','ingest_2016');

An AuditService with those five assertions, and a PASS/FAIL panel with Publish and Discard buttons, is the whole build.

Why it lands

Nobody querying main ever sees a partial or failed batch — a property most people's production pipelines don't have, achieved in an afternoon with no staging table, no second bucket, and no copy of the data. Deliberately corrupt a CSV row, watch the audit fail, watch main stay clean. Best five seconds of the day.

Concepts

Branching and tagging; atomic multi-file commits; why data-quality gates belong inside the table rather than in an orchestrator.

P3Compaction, and the economics of file size

40 minmediumSpace lanepairs with P5 or Core H4

Build a Maintenance panel, plus the measurements that justify it — file count, total size and query latency before and after each operation.

CALL lakekeeper.system.rewrite_data_files(
  table => 'housing.staging_prices',
  strategy => 'sort', sort_order => 'town ASC, date_of_transfer ASC');
CALL lakekeeper.system.expire_snapshots(...);
CALL lakekeeper.system.remove_orphan_files(...);

ALTER TABLE lakekeeper.housing.staging_prices ADD PARTITION FIELD years(date_of_transfer);

That last one surprises people: metadata-only, no data rewritten, old files keep their old layout and still read correctly. Have them prove it by counting files scanned before and after.

Concepts

The small-file problem; sort orders and Z-ordering as pruning strategy; hidden partitioning; and the tension worth arguing about — expire_snapshots destroys the time travel from P1. Retention is a policy decision, not a default.

P4MERGE, and making record_status mean something

45 minmedium-hardSpace lane

Build idempotent ingestion — fixing a real defect, since loading the same year twice currently doubles the rows and nothing prevents it.

MERGE INTO lakekeeper.housing.prices t USING staged_batch s
ON t.transaction_id = s.transaction_id
WHEN MATCHED AND s.record_status = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

The Land Registry's record_status column (A add / C change / D delete) has been sitting unused in the schema all day — the monthly change files are genuine CDC, and this is where the column finally earns its place. Then flip write.delete.mode to merge-on-read and measure both sides.

Concepts

Copy-on-write vs merge-on-read as write amplification against read amplification, with numbers they generated; idempotency as a design property; delete files and how compaction reclaims them.

Track B

Streaming

P5Kafka → Iceberg, live

60 minhardcompose lane · needs Docker

Build a streaming ingest path into the same table people have been querying all day. The connector is already installed in the repo's Connect image, so the work is:

  • a /admin/simulate endpoint producing synthetic transactions on the existing 16-column schema
  • a connector config POSTed to Connect on :8083 — Iceberg sink, REST catalog, iceberg.tables=housing.staging_prices, and a commit interval they get to tune
  • the query page left open, row counts climbing, queries still returning

Concepts

The commit interval as the latency/file-size dial — drop it to one second and watch P3's small-file problem appear in real time, which is the lab's best moment; exactly-once via the connector's control topic; readers never blocked by writers, the property that makes a table format viable for streaming at all.

Stretch: two connectors writing the same table concurrently. Optimistic concurrency handles it — make them find the retry in the logs.

Track C

Open format, many engines

P6One table, three engines

35 mineasy-mediumcompose lane · needs Docker

Build a /compare page that runs the same SQL through Spark and Trino and shows both result sets and both timings. Trino is already pointed at the same catalog with vended credentials, so this is a JDBC driver and a diff.

Then the moment that makes the point: write from Spark while Trino is connected and re-run the Trino query. New snapshot, immediately — no cache invalidation, no catalog reconfiguration, no export.

Concepts

What “open table format” actually buys: engine per workload, zero copies, no lock-in. This is the lab for a room that suspects lakehouse is a marketing word.

Track D

AI engineering

R2From one-shot generation to an agentic loop showstopper

50 minmedium-hardSpace laneneeds F1

Build a tool-calling agent that explores the schema before it writes anything. Spring AI 2.0 is already on the classpath and does this declaratively — @Tool methods registered with .defaultTools(…), where local tools and remote MCP tools share one ToolCallback interface, so anything built here also works through R5's MCP endpoint.

ToolWhy the model needs it
listTables()stop hardcoding the table name
describeTable(name)the live schema, not a string constant that rots
sampleValues(col, n)discovers property_type is D/S/T/F/O, not "Flat"
runSql(sql)F1's guarded, LIMIT-capped executor
explain(sql)check the plan before running something expensive

The loop is explore → write → execute → read the error → fix → answer. Make them deliberately break a query and watch the model recover.

Then measure it

Run F1's ten questions against one-shot and agentic, and fill in accuracy, p50 latency and tokens per question. Accuracy usually jumps; latency and cost usually go up three to five times. That table is the lab — “should this be an agent?” becomes a question with an answer instead of a preference.

R1The semantic layer, or: why text-to-SQL actually fails

45 minmediumSpace laneneeds F1

Ask the current app “how many flats sold in London last year?” and it fails twice, for reasons that have nothing to do with model quality: property_type is 'F', and “London” is a town value and 33 district values, with the right answer depending on which was meant.

Build three things: a YAML data dictionary of coded columns and synonyms; a distinct-value index over town/district/county embedded through HF Inference Providers (feature extraction is served by hf-inference, Scaleway and Together); and entity resolution at query time that hands the model resolved literals plus a disambiguation note.

Why it lands

Measured on F1's harness, this routinely moves accuracy more than any model upgrade from the F2 bake-off — a genuinely useful and slightly deflating finding for a room that just spent thirty minutes shopping for models. Most text-to-SQL failure is a data-modeling problem wearing an AI costume.

R3Semantic query cache

35 minmediumSpace lanepairs with R1

Build an embedding cache over incoming questions: on a close enough match, reuse the SQL — never the results, because the data moves — and skip the LLM entirely. Report hit rate, latency saved and cost saved.

The lab is the failure mode

“Average price in Camden in 2015” and “…in 2016” embed almost identically, and the naive cache returns confidently wrong SQL. The fix is normalizing entities and literals out of the question before embedding — exactly the machinery R1 built. Ship the naive version first, watch it break, then fix it. Nobody forgets a cache that lied to them.

Concepts

Embeddings for retrieval rather than generation; similarity thresholds as tunable risk; caching a plan not a result; a cache key must contain everything that changes the answer.

R4Query observability, published as a dataset

40 minmediumSpace laneneeds F1

Build end-to-end instrumentation: model id, provider, tokens, latency, the generated SQL, whether it parsed, whether it executed, rows returned, and Iceberg's own scan metrics (files scanned, bytes read). Write the traces to an Iceberg table — the app dogfooding its own warehouse — then publish it as an HF dataset repo so the Viewer and DuckDB console work over it for free.

The loop that closes

Production traces become next month's eval set; questions that failed become test cases. Scan metrics are also the bridge between “the query was slow” and “the table needs P3”.

A11Question → SQL → chart

30 mineasy-mediumSpace lanegood closer

Build the shape check in code, then a second structured-output call that picks a chart type from the ones code allowed and names the axes; code builds the Vega-Lite spec and renders it inline with htmx.

The interesting constraint is that the model must reason about result shape — one numeric grouped by one categorical is a bar; a date series is a line; forty thousand rows are a table and nothing else. Getting it to refuse to chart is harder than getting it to chart.

Why it's here

It's the most screenshot-able thing anyone will build all day, and short enough to finish. Sometimes that's the right lab.

Track E

Working with an agent

P15Drive a coding agent through an unfamiliar Java codebase

40 minany levelSpace lane

Build any other lab here — but with an agentic editor, where the real subject is how you drive it. P1 and A11 make the best specs: self-contained and visually verifiable.

  • Write an AGENTS.md for this repo first — where the Spark session is configured, that Thymeleaf fragments return template :: fragment, that admin endpoints are htmx POSTs, that Iceberg procedures live under <catalog>.system.*. Fifteen minutes here saves an hour.
  • Give the agent F1's eval harness as its feedback loop, so it checks its own work instead of asking. This is the biggest single difference between agent runs that converge and agent runs that wander.
  • Constrain the diff — one endpoint, one template, no refactors — and review it properly.

Then compare across the room

Who finished, what the agent got wrong, and where it confidently invented an Iceberg procedure name that doesn't exist. Version-specific API surface is where these tools reliably fail, and watching it happen live teaches verification better than any warning slide.

Reality check on timing

Ship a starter branch per lab

These durations assume attendees write real code and hit real errors. If the room is mixed in experience, hand out a branch with interfaces stubbed, tests written and the implementation removed. Nobody learns anything from the twenty minutes spent finding where to add a controller method — and the confident half of the room will finish the stretch goals anyway.
