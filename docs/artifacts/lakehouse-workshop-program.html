H2 · demo, not a lab5 min

Where the data actually lives

Run this straight after H1, while attendees still remember typing the APP_S3_* secrets — this is the explanation of what those secrets did. It also leaves F1 → F2 → A11 as one unbroken arc rather than splitting it with an infrastructure aside.

An Iceberg catalog knows where your table is; it does not care whose object store that is. Attendees have been proving that since the first load — on a bucket-backed Space the warehouse is on a Hugging Face bucket from the start, so there is nothing to move. Show it rather than build it.

Open their own bucket page at huggingface.co/buckets/<you>/warehouse, expand Iceberg's metadata/ and data/ directories, and open one Parquet file with pd.read_parquet("hf://buckets/…") — nothing Iceberg-aware in the path. Then say what would be sitting there if MinIO were in the way: <name>.parquet/xl.meta directories that no other tool can read. That contrast is the whole point.

This is the warehouse registration their setup click already posted, and it is worth putting on screen because three of its fields are counter-intuitive:

"storage-profile": {
  "type": "s3",
  "bucket": "<your-namespace>",   // the NAMESPACE, not the bucket
  "key-prefix": "warehouse",      // the bucket name goes here
  "endpoint": "https://s3.hf.co", // no path - LakeKeeper rejects one
  "region": "us-east-1",
  "path-style-access": true,
  "flavor": "s3-compat",
  "sts-enabled": false
}

Four gateway differences that are the actual lesson

  • No STS, so LakeKeeper hands out the access key rather than vending temporary credentials — a two-minute aside on why credential vending exists at all.
  • Path-style addressing is mandatory. Virtual-host style fails with “could not resolve hostname”, which looks like DNS and isn't.
  • The namespace becomes the S3 bucket. HF buckets are namespace/bucket, S3 won't take a / in a bucket name, and LakeKeeper won't take a path in the endpoint — so the real bucket name slides down into key-prefix.
  • ListObjectsV2 only; no versioning, ACLs, UploadPartCopy, or x-amz-meta-*. “S3-compatible” is a spectrum, and reading the compatibility notes before adopting a store is the professional lesson underneath the demo.
Why this stopped being a lab

It was a 35-minute exercise while MinIO was the default and moving off it was the exciting part. With bucket-backed Spaces the move happens before anyone arrives, so the payoff changed from watch it move to look where it already is. Keep the recipe below to hand: it is what you would walk through if you ever put attendees back on MinIO, and it is the troubleshooting sheet if someone's bucket setup misbehaves.

1. AWS SDK ≥ 2.5x with apache-client declared. This was the real blocker: Iceberg 1.9.2 on a 2024-era SDK produced a bare 403 with an empty body. S3FileIO still builds an ApacheHttpClient, and from the 2.5x line that artifact is no longer transitive — omit it and every call dies with ClassNotFoundException.

2. The endpoint may not have a path. LakeKeeper refuses it, so the HF namespace becomes the S3 bucket and the bucket name becomes key-prefix.

3. No explicit LOCATION. With a REST catalog the server places the table; anything else is rejected as an invalid location.

4. A token with read and write. Read alone authenticates perfectly and then refuses every PutObject with a bare AccessDenied … Unknown. Make the pre-flight a write, not a list.

F1 · the keystone40 min

Make the analyst trustworthy

Step-by-step build guide →

Three defects that were exercises in an earlier draft are already fixed in the code they clone — SqlGuard, SchemaStore and SqlAnswer. Attacking a working guard teaches more in forty minutes than building one, and a room of twenty-five cannot all get a parser-based guard running before the break.

Put this on the screen and ask what could go wrong:

Dataset<Row> resultsDF = spark.sql(generatedsql);  // HomeController

The answer they usually miss: generatedsql is a form field. The generated query lands in an editable textarea and whatever comes back is executed. No prompt injection required — type DROP TABLE and press Run.

1 · Break the guard — 15 min

AttemptResult
DROP TABLE …rejected — would modify the warehouse
SELECT 1; DROP TABLE …rejected — fails to parse
INSERT INTO … SELECT · MERGE · DELETErejected — writes
CALL …rollback_to_snapshot(…)rejected, but via NoClassDefFoundError
WITH x AS (SELECT …) SELECT * FROM xruns — a CTE is a read
SELECT/**/town FROM …runs — comments change nothing

The debrief is the last two rows. A regex would have rejected the CTE and been fooled by the comment. The parser asks Spark what the text means, not what it looks like. And CALL is why the guard catches Throwable: Iceberg's parser throws an Error, and "cannot confidently parse this" and "will not run it" are the same answer.

2 · Where a row limit belongs — 10 min

Try the Rows to return field at 3, 7, then 500. Three places you could put a limit: the prompt (the model complies sometimes — this repo has the git history), render time (count() already scanned everything), or .limit(n) in the plan. Only the third bounds the work. 500 comes back as 200, because a user-supplied bound still needs a bound.

3 · The deliverable: an eval set — 20 min

Ten questions with known-correct answers in a CSV, and a runner scoring four cumulative gates: generated? → parses? → executes? → correct? plus latency. The order matters — 10/10/10/3 is a completely different problem from 10/4/4/4.

Where attendees stall

They try to invent the expected answers. They should derive them: run the query by hand in the box, read the answer, record it. Writing the ten questions is the exercise, because it forces them to decide what "correct" means.

Say two things before they start: ten questions is ten inference calls per run on their own credits, so start with five — and run it twice on the same model. The scores will differ, and that non-determinism is what most of the room has never measured. Debrief question: "how many runs before you would believe a prompt change helped?"

Model bake-off on Inference Providers

Step-by-step build guide →

First half of the lab: make the model a runtime parameter. It's currently pinned in application.properties and baked into the ChatClient at construction, so comparing four models the obvious way costs four deploys. One push fixes it — have generateQuery() take a model name and set it per call with OpenAiChatOptions.builder().model(id). After that, the whole bake-off runs with no further deploys, and F1's harness can loop over all four models in a single run.

A11 · first AI feature30 min

Don't make me read a table

Step-by-step build guide →

Priya, who builds client decks: “When I ask how prices have moved in Camden I get two hundred rows of numbers. I need the picture. I'm currently rebuilding every one of them in Excel.” Results should render as the right chart automatically.

Build it as constrain-then-ask: compute the shape of the result — column types, cardinality, row count — and let code decide which chart types are legal. A second structured-output call picks one of those and names the axes; code builds the Vega-Lite spec and renders it inline with htmx. A time series becomes a line, one category plus one measure becomes bars, two measures become a scatter.

The interesting problem — and the debrief

Choosing the chart is easy; refusing is hard, and it is where every naive version falls over. More than two dimensions, tens of thousands of rows, or a single scalar should render as a table with a one-line reason, not a broken chart. Push them to compute the result shape first and let the model choose only within what is legal — constrain, then ask. That ordering is the transferable lesson.

Ask the room: “what happens when the query returns one number?” Most teams won't have handled it, and a giant single-bar chart in a client deck is worse than a table.

Scope for a 30-minute slot

The full ticket is 40 minutes. Drop the “Priya can override the chart type and it sticks” criterion and it lands in 30 — keep chart selection and the refusal path, because the refusal is the part worth debriefing. Visually self-verifying, so nobody sits stuck without knowing it.

Useful anywhere ✓ structured output against a validated schema Better on HF ✓ any Inference Provider model, swapped from the admin page
H4 · pick one30 min

Get the ingest off the Space

Stated honestly: Download and Load run inside an HTTP request, on 2 vCPU, with no progress and no retry. One year is tolerable; eleven is not. This is the batch/serving split, and it's an architecture lesson before it's an HF lesson.

hf jobs uv run ingest.py --with duckdb \
  -v hf://buckets/<you>/warehouse:/mnt/warehouse \
  --flavor cpu-performance --timeout 1h

hf jobs logs <job-id> --follow

Then right-size it: run the same job on cpu-basic ($0.01/h) and cpu-performance ($1.90/h) and compare wall-clock against total cost. The expensive flavor usually turns out cheaper per job — a counterintuitive result people remember.

Stretch: hf jobs scheduled run '0 6 1 * *' for the monthly Land Registry release, or a Hub webhook that re-fires ingest when the upstream dataset repo changes.

Step-by-step build guide →

Turn the lakehouse into a tool an agent can call

spring-ai-starter-mcp-server-webmvc is already in pom.xml and completely unused — nothing in src/ mentions MCP. So there's a real, small, satisfying build here: expose describe_table() and run_query(sql) over the Space's existing port, point an agent at https://<you>-big-data-ai.hf.space/mcp, and ask it a question in English.

It writes SQL, runs it against their warehouse, and reasons about the result — with F1's guardrail refusing anything that isn't a SELECT. Dev Mode — fix a bug without the rebuild

If most of the room is on PRO, this lands harder, because a Docker Space rebuild is 8–15 minutes and Dev Mode skips it entirely. And this repo isn't Dev Mode compatible yet — making it so is the exercise. Against the documented requirements the Dockerfile already has a Debian base, /app owned by uid 1000, and curl. It's missing wget, procps, git, git-lfs — and a CMD instruction, since the image only declares ENTRYPOINT.

Add the four packages, convert ENTRYPOINT to CMD, push, then hf spaces dev-mode and hf spaces ssh. Edit a prompt in the running container, hit Refresh, see it live — then git push from inside the Space to persist it, because Dev Mode changes are otherwise discarded. Demonstrate that foot-gun deliberately rather than letting someone discover it.

How expensive is a rebuild, actually

Measured today, so these are real rather than guessed:

BuildTime
First build — docker build --no-cache, wall clock70 seconds; 64 s of it is one step, mvn dependency:go-offline. apt-get install postgresql-18 was 10 s, everything else under 5 s
Subsequent push, one Java file changed — on Hugging Faceunder 60 seconds, from this Space's own build logs
The same warm rebuild locally~5 seconds — dependency:go-offline CACHED, mvn package 3.1 s, every apt/MinIO/LakeKeeper layer CACHED

Two things make this cheap, and both are already true of the Dockerfile as written. The layer order is right — COPY pom.xml and dependency:go-offline come before COPY src, so a source change never re-resolves the Spark dependency tree; that 64-second step is paid once and then cached. And Hugging Face reuses Docker layers between commits, so attendees get the warm path from their second push onwards.

How attendees iterate — push to the Space

The default and documented loop is push-to-deploy. Edit locally, commit, push, watch the build. Nothing is installed and nothing is downloaded: after the clone, each push is a few kilobytes of diff, and every heavy thing happens on Hugging Face's builders rather than on the venue's wifi.

StepTime
git push hf mainseconds — the diff is tiny
Build on HF, layers cachedunder 60 s
Space restart (Postgres, LakeKeeper, MinIO, then the app)~20–40 s
Round tripabout 1½–2 minutes

Slower than a local restart, and completely workable provided the labs are designed around it:

  • Batch the edit, then push. Write the whole change and push once; read hf spaces logs --build --follow while it runs.
  • Make the thing you're iterating on a runtime parameter. Worth more than any deploy trick. F2 is the example: rather than four deploys to try four models, spend the first push making the model a per-request option, then run the whole bake-off with no further deploys.
  • Space variables do not avoid a build. Measured 2026-09-02: hf spaces variables add puts the Space through RUNNING → RUNNING_BUILDING → RUNNING_APP_STARTING and the build log gains an entry. It takes the cached path and the old container keeps serving throughout, so there's no downtime — but it costs about the same as a push. Use variables because they can't introduce a compile error, not because they're free.
  • Pair up. Two per Space halves the round trips and gives one person the build log while the other writes code.
  • Dev Mode is the real fix if the room has PRO — SSH in, edit, Refresh, no rebuild at all.
Why not a local loop

Running the stack locally needs Docker Desktop, JDK 21 and Maven, and pulls roughly 700 MB per person — about 220 MB of images (postgres:18-alpine 112 MB, minio 55 MB, lakekeeper ~50 MB compressed) plus ~500 MB of Maven dependencies (Spark alone is 350 MB). Across 25 people that's ~17 GB over the venue wifi. Anyone who wants it should run docker compose pull and mvn dependency:go-offline before they travel.

Local development — optional, and for you rather than the room

Verified on Apple Silicon, 2026-09-02. This is how you build the material. Build the jar on the host and mount it into the container — no image rebuild at all. Two variants, and the choice is speed against fidelity:

LoopEdit → liveWhat it restarts
compose + jar mounted into app, then docker compose restart app~9 s (6.3 s Maven + 3.1 s restart)only the app container — Postgres, MinIO and LakeKeeper keep running untouched
single container + jar mount, then docker restart~13 s (6.3 s Maven + 6.3 s restart)the whole stack — but it is the real Spaces topology, so use it before pushing

For the compose variant, put the mount in a dev-only compose.override.yaml (merged automatically; add it to .gitignore):

services:
  app:
    volumes:
      - ./target/big-data-ai-0.0.1-SNAPSHOT.jar:/app/app.jar:ro

Why only the compose variant can restart just the app: in the single-container image the entrypoint deliberately runs java … & and waits on it, so it stays PID 1 and can take a final catalog dump on shutdown — killing the JVM there stops the container. Where the app is its own container, process separation is already container separation.

# single-container variant
docker build -t big-data-ai-app .        # once; ~5 s after the first time

docker run -d --name big-data-ai \
  -p 7860:7860 -p 8181:8181 -p 9000:9000 -p 9001:9001 \
  -v "$PWD/data":/data \
  -v "$PWD/target/big-data-ai-0.0.1-SNAPSHOT.jar":/app/app.jar:ro \
  --env-file .env big-data-ai-app

mvn -o -q -B -DskipTests package && docker restart big-data-ai

The entrypoint runs java … -jar /app/app.jar, so mounting your jar over that path is the whole trick. Verified by checksum inside the container, and by a template change appearing on the next request. It also sidesteps the endpoint bug below, because the app is back inside the container's network namespace.

The alternative — compose services plus mvn spring-boot:run on the host — restarts faster but doesn't exercise the entrypoint, and needs 127.0.0.1 minio lakekeeper in /etc/hosts to work at all:

docker compose up -d lakekeeper   # pulls in db, migrate, minio — not app or trino
mvn spring-boot:run               # no APP_* overrides needed, given the hosts line
The bug the hosts line avoids — reproduced today

The README says to override APP_S3_ENDPOINT=http://localhost:9000. That's right for the app's own S3 client and wrong for LakeKeeper, because the same string is embedded in the warehouse definition the app POSTs, and LakeKeeper dials it too.

Inside the LakeKeeper container, localhost:9000 is LakeKeeper's own Prometheus metrics endpoint — its metrics port defaults to 9000, and while the Dockerfile moves it to 9191 for the single-container case, compose.yaml does not. Warehouse validation does an S3 GetObject against it, gets Prometheus text, tries to gunzip it, and returns 400 FileDecompressionError: invalid gzip header — which IcebergService.setup() catches and reports as “Warehouse already exists - skipping…”.

So Setup claims success, and GET /management/v1/warehouse returns {"warehouses":[]}. The hosts line fixes it with no code change: one string now resolves to MinIO from both vantage points. The proper fix is to split app.s3.endpoint from the value handed to the catalog — twenty minutes, and an honest addition to F1's defect list, since the root cause is the same swallowed 400.

The obvious Hugging Face workshop is fine-tune a model, push it to the Hub, deploy it in a Space. There are a hundred of those, and the people who signed up for a data-engineering session don't want it.

This set uses the Hub as infrastructure for a data platform — object storage, batch compute, a model router, a publishing surface, an agent endpoint. That's both the less-told story and the one that maps onto the systems these attendees actually run at work. The Iceberg table sitting in an HF bucket is the image they'll describe to a colleague on Monday.
