Lab A10 · Meridian ticket · 60 minutes · you write the code

Give me comps I can defend

An address in; comparable sales, a valuation range, and a written justification out — where every number in the prose traces to a row in the table.

The ticket · Marcus, valuing property for lenders

"I'm valuing 14 Acacia Road, SW11. I need the comparable sales and a range I'd be willing to put in front of a lender. Right now I'm doing this by hand and it takes forty minutes a property."

The one rule that makes this lab worth an hour

Compute first, narrate second. Your code selects the comparables and computes the range. The model's only job is to write the paragraph — it must never produce a number that is not already in your table.

Get that ordering wrong and you have built something that invents valuations for lenders. Get it right and you have the single most reusable pattern in the whole workshop.

Part 1

Comparable selection is policy, not a query

10 min
1.1

Pick a real subject property

Use the app or Sample rows to find one, and write down its postcode, district, property_type, duration and date_of_transfer. That row is your subject; everything else is evidence.

1.2

Write the strict rule first, in SQL, by hand

Before any code, run this in the SQL box and see how many rows you get:

SELECT price, date_of_transfer, paon, street, postcode
FROM lakekeeper.housing.staging_prices
WHERE district      = '<subject district>'
  AND property_type = '<subject type>'
  AND duration      = '<subject tenure>'
  AND date_of_transfer >= '2015-01-01'
ORDER BY date_of_transfer DESC
Notice what just happened

Depending on the property you picked, you got plenty — or almost nothing. That is the entire feature. Comparable selection is a business rule with consequences, and the rule that is right for a terraced house in Leeds is wrong for a detached house in a village with four sales a year.

Part 2

The degradation ladder

15 min
2.1

Decide the ladder before you write it

When strict does not find enough evidence, relax one rung at a time, and record which rung you are on. A defensible suggestion:

RungRelaxStill holds
0nothing — same district, type, tenure, 12 monthseverything
1widen to 24 monthsdistrict, type, tenure
2widen to the countytype, tenure
3drop tenuretype
—Stop. Fewer than 5 comps after rung 3 is "insufficient comparable evidence", not a wider search
2.2

Build it

new file · src/main/java/dev/prpatel/iceberg/app/CompsService.java 
public record Comps(
        List<Row> rows,
        int rungUsed,
        String rungDescription,   // "same district and type, widened to 24 months"
        boolean sufficient) {}

// Walk the ladder. Stop at the first rung with >= 5 rows. Cap at 15.
// Return sufficient=false rather than a wider search.
Two things to get right
  • Between 5 and 15. Two sales is not evidence; two hundred is not comparable. Both ends matter
  • Carry the rung out with the rows. "Which rule produced this?" is the question a lender asks, and you cannot answer it later if you did not record it
Part 3

A range, not a number

10 min
3.1

Choose your statistic, and be able to defend it

You have between 5 and 15 prices. Turning them into a range is a decision, not a formula you look up:

OptionArgument against it
min to maxone odd sale drags the whole range open
interquartile rangehonest, but with 6 comps the quartiles are two data points
trimmed mean ± spreadneeds you to justify what you trimmed and why
Write down which you chose and why

This is the part a lender will actually challenge. "The tool said so" is not an answer, and whichever you pick, the number of comparables has to be visible next to the range — a range from 6 sales and a range from 15 are not the same claim.

Part 4

Narrate — and only narrate

15 min
4.1

The model gets facts, not a question

By now everything is computed. The prompt hands the model the finished numbers and asks for prose:

Give it
  • the subject property
  • the comparable rows, as data
  • the range you computed, and the count behind it
  • the rung description — "widened to 24 months to find enough evidence"
And tell it, explicitly

Use only the numbers provided. Do not compute, estimate or round anything. If a figure is not in the data given, it must not appear in the paragraph.

4.2

Then verify it, in code

Instructions are not a guarantee — F2 part 2.3 showed you a model ignoring a contract outright. So check:

// pull every number out of the generated prose and assert each one
// appears in the comps, the range, or the count
Pattern.compile("£?[0-9][0-9,]*")
Then decide what to do when it fails

Reject and retry? Show the paragraph with the invented figure flagged? Fall back to the table alone? There is no right answer — but a valuation tool that quietly passes through a number it made up is the worst of the three, and that is the one you get by not deciding.

Part 5

Break it on purpose

10 min
5.1

Find a property with almost no comparables

A rare property type in a thin district. Run your feature against it.

The three questions
  1. Did it say "insufficient comparable evidence" — or did it produce a confident range from three sales?
  2. Is the relaxation visible to Marcus, or did it silently widen until it found something?
  3. Would you put the output in front of a lender?
—

Done when

—
Between 5 and 15 comparables, or an explicit refusal — never a confident answer from two sales
The selection rule is shown, including any relaxation
A range, with the number of comparables behind it visible
Every figure in the prose traces to a row — and you check it in code rather than trusting the prompt
