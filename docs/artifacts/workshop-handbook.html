Lakehouse Workshop Handbook

The four-hour plan, the mechanics attendees need, and the operational notes that only existed in chat until now — plus an index of the five detail pages.

The four hours

Built to your format: a 30-minute opener, then a 15-minute lecture at the top of each hour followed by hands-on. Reordered for the AI-features direction.

The rule that shapes everything below

Almost every LLM-feature exercise is Java, and each deploy is a ~90 s round trip. A four-hour day therefore holds at most two feature tickets. Hours 1 and 4 are padded with CLI-only work so the room isn't waiting on you and on each other at the same time.

On promoting Hugging Face in an AI-features day

You don't need H2 and H3 to make the HF case — every exercise in hours 2 to 4 runs on Inference Providers, and hour 1 is Spaces, Buckets and secrets end to end. The platform labs add storage and publishing to that; they aren't carrying the argument on their own.

What attendees actually do

Pre-work — send a week ahead, remind the night before

Step 1 — create one token with Full Access. At hf.co/settings/tokens: New token → type Fine-grained → name it workshop → click the Full Access preset → Create. Copy it; it is shown once.

That covers everything the day needs — creating a Space and a bucket, pushing over git, calling Inference Providers, starting Jobs, publishing a dataset, and the S3 credentials H2 derives from the token. Everything lives in the attendee's own namespace, so only the User permissions section matters; there is no organisation involved.

Step 2 — install the CLI and log in. The installer needs Python 3.10+ already on the machine — it does not install Python for you. It probes for python3, and if nothing suitable is found it prints instructions and exits having installed nothing. It then builds a virtualenv and pip-installs into it, so Debian/Ubuntu needs python3-venv too. On macOS a good Python is often present but shadowed by an older one earlier in PATH; the installer says so and names the directory to move up.

python3 --version
# must print 3.10 or newer. If not, install Python first:
#   macOS          brew install python
#   Debian/Ubuntu  sudo apt update && sudo apt install python3 python3-venv
#   Fedora/RHEL    sudo dnf install python3 python3-pip

curl -LsSf https://hf.co/cli/install.sh | bash -s
hf auth login --token hf_xxx --add-to-git-credential   # --token required: browser login ignores the flag
hf auth whoami

Step 3 — the pre-flight, and the second call is the one that matters.

# inference works and the credit is on the account
curl -s https://router.huggingface.co/v1/chat/completions -H "Authorization: Bearer $(hf auth token)" -H "Content-Type: application/json" -d '{"model":"openai/gpt-oss-120b:cheapest","messages":[{"role":"user","content":"say ok"}]}'

# the token can WRITE - a read check passes with a read-only token and proves nothing
hf buckets create <you>/preflight --private
hf buckets delete <you>/preflight --yes

Plus git and an editor. No Docker, no Java, no Maven — the whole day is push-to-deploy, deliberately, because the local stack is ~700 MB of pulls per laptop and conference wifi won't carry 25 of those.

Why Full Access, and not the six boxes that are actually used

Six permissions are genuinely needed: repo read and write, Make calls to Inference Providers, Start and manage Jobs, plus collections and webhooks for the closing demo and stretch goals. Ticking exactly those works.

Do not do it in a workshop. A token missing one box authenticates perfectly and then refuses the operation with AccessDenied … Unknown, naming no permission — verified the hard way on 2026-09-05, where read-without-write cost an hour of debugging with full context and a shell. In a room of twenty-five that is unrecoverable, and the token is a throwaway for one day on one account.

Attendees run on their own credits, so there is no organisation, no --namespace on Jobs, and no X-HF-Bill-To — everything bills to them. That header is now a setting rather than a source edit — APP_AI_BILL_TO, empty by default — so attendees leave it alone, while a Space deployed inside an org sets it to the org name. Both directions fail the same way when wrong: a 500 hiding 403 “does not have sufficient permissions to call Inference Providers on behalf of user <you>”, which reads like a broken token and is not.

First deploy — hour 1, first five minutes

The commands live in one place

Attendee setup, in full, further down this page. Do not assemble the sequence from memory or from this section: the seven APP_S3_* variables are what decide whether the Space stores its table on a Hugging Face bucket or falls back to an embedded MinIO, and skipping them fails silently — the build succeeds, the app starts, and the warehouse is simply in the wrong place. There is no error to notice.

The one line that proves it went right, in the boot log: [init] EMBEDDED_MINIO=0; the warehouse lives in external storage (https://s3.hf.co). No such line means MinIO, whatever else looks healthy.

--force on the first push is expected, not a mistake: hf repos create initialises the Space with its own README commit, so local main is unrelated history.

2b

Two storage paths, and who configures each

A bucket-backed Space writes to Hugging Face storage two different ways, and only one of them is a volume. This is the part that confuses people, so put it on a slide.

What happens
1Setup Environment is where the location is stated — once. The app takes the APP_S3_* settings and POSTs them to LakeKeeper as a storage profile: endpoint, bucket, key-prefix, region, STS flag, access key. Nothing else hardcodes where data lives
2LakeKeeper persists it in Postgres against the warehouse named lakehouse. That is how it knows where to look — you told it at Setup and it kept it
3At load or query time the catalog answers with a location. Spark asks "where does this table live?" and gets an s3://… back. This is why nothing outside Setup needs to know the bucket
4Spark writes the parquet straight to the bucket through s3.hf.co, at the location it was just given
5CSVs and exports are ordinary file writes to the mounted volume — no S3, no catalog
6The catalog database is dumped to the same volume every 60 s and on shutdown, which is what makes the whole thing survive a restart
Why the key appears twice

Normally the catalog vends credentials as well as locations. The HF gateway has no STS, so APP_S3_CLIENT_SIDE_SIGNING=true hands Spark the same access key to sign its own requests. LakeKeeper needs it to validate the profile and write metadata; Spark needs it to write data files. Two consumers, one key.

Attendee setup, in full

# ---- 1. the code -------------------------------------------------------
git clone https://github.com/prpatel/big-data-ai big-data-ai
cd big-data-ai

# ---- 2. the Space ------------------------------------------------------
# cpu-upgrade, not the free cpu-basic: that is what the timings assume
hf repos create <you>/big-data-ai --repo-type space --sdk docker --private --flavor cpu-upgrade

# ---- 3. two buckets ----------------------------------------------------
# lakehouse: ordinary files - CSVs, catalog dump, the export
hf buckets create <you>/lakehouse --private
# warehouse: the Iceberg table, over the S3 API, NEVER mounted
hf buckets create <you>/warehouse --private
# only lakehouse is mounted, as the Space's /data
hf spaces volumes set <you>/big-data-ai -v hf://buckets/<you>/lakehouse:/data
hf spaces volumes ls <you>/big-data-ai

# ---- 4. S3 credentials: browser only ------------------------------------
# tokens page -> the token's ... menu -> Generate S3 credentials
# HFAK... access key + a secret shown exactly once

# ---- 5. settings, from a file rather than seven flags -------------------
cat > space.env <<'EOF'
APP_S3_ENDPOINT=https://s3.hf.co
APP_S3_BUCKET=<you>
APP_S3_KEY_PREFIX=warehouse
APP_S3_STS_ENABLED=false
APP_S3_CREATE_BUCKET=false
APP_S3_CLIENT_SIDE_SIGNING=true
APP_WAREHOUSE_EXPLICIT_LOCATION=false
EOF

cat space.env                  # check <you> is your username in BOTH places
hf spaces variables add <you>/big-data-ai --env-file space.env
hf spaces variables ls <you>/big-data-ai    # must list all seven

# ---- 6. the three secrets, one at a time --------------------------------
hf spaces secrets add <you>/big-data-ai -s HF_TOKEN=hf_xxx
hf spaces secrets add <you>/big-data-ai -s APP_S3_ACCESS_KEY=HFAK...
hf spaces secrets add <you>/big-data-ai -s APP_S3_SECRET_KEY=...
hf spaces secrets ls <you>/big-data-ai      # names only, never values

# ---- 7. deploy -----------------------------------------------------------
git remote add hf https://huggingface.co/spaces/<you>/big-data-ai
git push --force hf main

# ---- 8. watch it, then prove it is bucket-backed -------------------------
hf spaces logs <you>/big-data-ai --build --follow
hf spaces wait <you>/big-data-ai
hf spaces logs <you>/big-data-ai --follow   # the runtime log - keep it open all day
hf spaces logs <you>/big-data-ai | grep EMBEDDED_MINIO
#   [init] EMBEDDED_MINIO=0; the warehouse lives in external storage (https://s3.hf.co)
# ---- 9. load the data, at https://<you>-big-data-ai.hf.space/admin ------
# Keep the runtime log open. All three buttons say "... operation initiated"
# whether or not they worked - the log is the only place the truth is.
#
#   Setup Environment   ~10s  -> Warehouse created (or "already existed; updated")
#   Download Data 2015  ~1m   -> Downloaded pp-2015.csv, about 170 MB
#   Load Data     2015  ~30s  -> Data loaded successfully
#
# Then confirm it, in the SQL box on the home page:
#   SELECT COUNT(*) FROM lakekeeper.housing.staging_prices   -> about about 1.01 million
# If you get 0, the load failed. Read the log; do not just click Load again.
The setting everyone will get wrong

APP_S3_BUCKET is your username, not the bucket name. LakeKeeper refuses an endpoint carrying a path, and HF buckets are addressed as namespace/bucket — so the namespace has to play the part of the S3 bucket, and the real bucket name becomes APP_S3_KEY_PREFIX. It reads wrongly and is correct.

Generating the S3 credentials is UI-only, once per attendee — no CLI, no API. Budget five minutes, and expect a few people to swap the key and the secret. H2 also stops being a lab, since what it teaches is now the starting state. To keep it hands-on instead, put attendees on MinIO — drop the second bucket, the two APP_S3_* secrets and the whole variables block — and make only your own Space bucket-backed for the demo.

Operational notes — for you

Everything here was measured or reproduced on this machine, not estimated.

Your local loop

# compose.dev.yaml — tracked, opt-in, mounts the jar you just built
services:
  app:
    pull_policy: build        # else compose tries to PULL big-data-ai-app and fails
    volumes:
      - ./target/big-data-ai-0.0.1-SNAPSHOT.jar:/app/app.jar:ro
./local-build-deploy.sh          # build + restart + wait  (~10 s)
./local-build-deploy.sh -n       # restart only          (~3 s)
./local-build-deploy.sh -l       # ... then follow the app log
./local-build-deploy.sh -d       # stop the stack

App on :7860, MinIO console on :9001, LakeKeeper on :8181. Logs: docker compose -f compose.yaml -f compose.dev.yaml logs -f app, or docker logs -f big-data-ai-app-1.

Three traps

1 · The admin buttons always claim success. AdminController adds "… operation initiated." unconditionally. The real outcome only reaches the log. Teach hf spaces logs --follow in the first ten minutes.

2 · Running the app on your host breaks Setup. The README's APP_S3_ENDPOINT=http://localhost:9000 is right for the app and wrong for LakeKeeper, whose own metrics endpoint is on 9000 inside its container — warehouse validation gets Prometheus text, tries to gunzip it, returns 400 invalid gzip header, and the app swallows it as "Warehouse already exists". Add 127.0.0.1 minio lakekeeper to /etc/hosts and drop the overrides, or use the jar-mount loop instead.

3 · A stale AWS SDK produces a bare 403. Iceberg 1.9.2 against SDK 2.25.58 fails every write to s3.hf.co with an empty-bodied 403. Upgrading to 2.54.13 and declaring software.amazon.awssdk:apache-client fixes it — S3FileIO still builds an ApacheHttpClient and that artifact stopped arriving transitively.

4 · Two unauthenticated LLM endpoints. /ai/simple and /ai/prompt in LLMController are public GETs that bill real inference calls and aren't used by anything. Delete them before the Spaces go public.

Prep & cost

#Task
1Rehearse the whole attendee path from a personal, non-org account — new Space, two buckets, S3 credentials, push, Setup, Load, ask a question. That is the only way to catch a token policy or a billing setting that blocks the room. Leave APP_AI_BILL_TO unset for that run: attendees are not org members
2Write the starter branch for hours 2 and 3: stubs, tests, and the eval CSV. Without it, half the room spends twenty minutes finding where to add a controller method
3Mirror pp-2015.csv into a public HF bucket so 25 people don't hammer the Land Registry origin
4Consider upgrading Spaces to cpu-upgrade — ~$3 for the day, and it takes the first Load off the critical path
5If you run Variant B, dry-run H2 and pin the working storage-profile JSON

Total compute for 25 attendees over four hours lands around $20–40 — Spaces are near-free, inference is the bulk, buckets are within the free allowance.
