big-data-ai · one-time bootstrap

Iceberg Setup Runbook

Four clicks on /admin take a cold container to a queryable Iceberg table: create the warehouse, pull a year of UK Price Paid data, load it through Spark, then ask questions in English.

App localhost:7860 Catalog LakeKeeper :8181 Storage MinIO :9000 / :9001 Table lakekeeper.housing.staging_prices
0

Run the stack

One image carries the app, Postgres, LakeKeeper and MinIO; docker-entrypoint.sh starts them in dependency order and symlinks /app/data onto the mounted volume, so downloaded CSVs survive a restart.

docker build -t big-data-ai-app .

docker run -d --name big-data-ai \
  -p 7860:7860 -p 8181:8181 -p 9000:9000 -p 9001:9001 \
  -v "$PWD/data":/data \
  --env-file .env \
  big-data-ai-app

docker logs -f big-data-ai   # leave this running — see the callout below

HF_TOKEN in .env is only read by Generate Query. Setup, download and load all work without it.

Read the logs, not the page

Every admin button answers “… operation initiated.” — AdminController adds that message unconditionally after the service call returns. It is not a success signal. The real outcome (✅ or Error …) is printed to stdout only, so keep the log tail open for all three steps.

When Spring Boot reports it is up, open http://localhost:7860/admin.

1

Setup Environment

Click Setup Environment. That posts to /admin/setup, which calls IcebergService.setup() and does three things in order — all of them idempotent, so re-clicking is safe.

a CreateBucket("warehouse") against MinIO Credentials come from app.s3.access-key / app.s3.secret-key, defaulting to minio / minio1234. A 409 (bucket exists) is swallowed.
b POST /management/v1/bootstrap to LakeKeeper Accepts the terms of use. A 400 logs “already bootstrapped — skipping”.
c POST /management/v1/warehouse to LakeKeeper Registers warehouse lakehouse over the warehouse bucket: path-style access, flavor: minio, STS enabled.

Both LakeKeeper calls go through the Management API with a plain HttpClient — that is deliberately not the Iceberg REST catalog protocol, which is why RESTCatalog isn’t used here.

Verify

Three ✅ lines in the log, and a warehouse bucket visible in the MinIO console at localhost:9001 (minio / minio1234).

Two names that must match

The warehouse is registered as lakehouse, and SparkConfig asks for spark.sql.catalog.lakekeeper.warehouse=lakehouse. The credentials are settings rather than literals now, but both sides still have to agree: change MINIO_ROOT_USER / MINIO_ROOT_PASSWORD and you must set APP_S3_ACCESS_KEY / APP_S3_SECRET_KEY to match, or this step fails.

2

Download Data

Type a year — 2015 — into the Year field under Download Data and click the button. IcebergService.download() fetches one CSV of HM Land Registry Price Paid records, roughly a million rows:

http://prod.publicdata.landregistry.gov.uk.s3-website-eu-west-1.amazonaws.com/pp-2015.csv
  → ./data/house_prices/pp-2015.csv      # /app/data → the mounted volume
· Leave the year blank and it pulls 2015 through 2025 Ten parallel downloads, capped at a pool of 10. That range is hardcoded — the 2023 in the input placeholder is just placeholder text.
· A year already on disk is skipped Skipped: pp-2015.csv (already exists) — safe to re-click.
· A year outside 2015–2025 fails quietly The upstream returns a non-200 and it is logged as Failed:; the page still says “initiated”.
Verify

✓ Downloaded: pp-2015.csv in the log, then reload /admin — the “Files already downloaded” list is rendered on GET /admin only, so it never refreshes on its own.

3

Load Data

Enter the same year under Load Data and click. This is the step that actually touches Iceberg, via the Spark session running embedded in the app:

1 CREATE NAMESPACE IF NOT EXISTS lakekeeper.housing
2 CREATE TABLE IF NOT EXISTS … staging_prices … USING iceberg Sixteen columns, each carrying a COMMENT lifted from the Land Registry field docs, at LOCATION 's3://warehouse/housing/staging'.
3 Read the CSV headerless against an explicit schema date_of_transfer arrives as text and is parsed with to_date(…, "yyyy-MM-dd HH:mm"), then the columns are re-selected in table order.
4 writeTo("lakekeeper.housing.staging_prices").append() Parquet data files land in MinIO; only the snapshot metadata goes to LakeKeeper and its Postgres.
Three things that bite

Order is load-bearing. Load before Setup and the table’s s3://warehouse location has no registered warehouse behind it. Load before Download and you get one File not found line in the log — the page still reports success.

It appends, it does not upsert. Loading the same year twice doubles the rows. Clear the table first if you need to redo a load.

A blank year loads every file in data/house_prices (.gitkeep excluded).

Verify

✅ Data loaded successfully from data/house_prices/pp-2015.csv. Spark runs local[*] inside the app process, so a full year takes minutes and real memory — that line is the only progress indicator you get.

4

Ask it something

Go to http://localhost:7860/.

Generate Query

POST /generatequery — your question plus the table’s column schema go to the chat model. The schema is read from the catalog with DESCRIBE TABLE and cached, so adding a column shows up without a rebuild; the model is whichever the Model Picker on /admin is set to. It returns JSON — sql, columns_used, assumptions — because the system prompt asks for it.

Run Query

POST /runquery — the SQL is handed straight to spark.sql() against the Iceberg table. The first 100 rows are rendered.

The SQL sits in an editable box between the two, so a query that comes back slightly wrong can be fixed by hand before running.

What each click actually touches

Three buttons, three different halves of the stack. Only step 3 goes through Spark; steps 1 and 2 are plain HTTP from the Spring app.

What to re-run, and when

The steps are not equally repeatable. Setup is once per data root; the other two are per unit of data, and only one of them has an undo.

Where state lives

CSVs under DATA_ROOT/app/house_prices, Iceberg data in DATA_ROOT/minio, catalog as a periodic pg_dump to lakekeeper-catalog.sql. Postgres itself is rebuilt from that dump on every boot.

Running from source

Start the container without publishing 7860, then point the app at the host: APP_CATALOG_URI, APP_CATALOG_BASE_URL and APP_S3_ENDPOINT must all be overridden — the defaults are compose service names that don’t resolve from the host.

On Hugging Face Spaces

Only port 7860 is published, and the Hub page is an iframe wrapper that doesn’t proxy sub-paths. Reach the admin page at https://<owner>-<name>.hf.space/admin, not through the Hub URL.
