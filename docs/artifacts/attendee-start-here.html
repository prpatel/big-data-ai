Lakehouse + AI workshop · start here

Everything you need, before and during the day

Four hours taking an Iceberg/Spark app from a laptop demo to a lakehouse running on Hugging Face, with an AI analyst on top. Part 1 below is the pre-work — do it before you arrive, or you will spend the first hour catching up.

Part 1

Before you arrive

Twenty minutes, done at home. Everything after this assumes it. Tick items off as you go — this page remembers on this browser.

1 · Create one token with Full Access

At huggingface.co/settings/tokens: New token → type Fine-grained → name it workshop → click the Full Access preset → Create. Copy it now — it is shown once.

Everything lives in your own namespace, so only the User permissions section matters. Full Access is deliberate: a token missing one box authenticates perfectly and then fails later with AccessDenied … Unknown, naming no permission.

2 · Generate S3 credentials from that token

Same page. Click the ⋯ beside the Full Access token you just made → Generate S3 credentials. You get an access key starting HFAK… and a secret shown exactly once. Copy both somewhere before leaving the page.

The one everybody hunts for

These come from the token, not from a bucket or a storage page. If you are looking at a bucket trying to find them, you are on the wrong page.

3 · Install the CLI and log in

The installer needs Python 3.10+ already on your machine — it does not install Python for you. It looks for python3, and if it finds nothing suitable it prints instructions and stops, having installed nothing.

python3 --version
# must print 3.10 or newer. If not, install Python first:
#   macOS          brew install python
#   Debian/Ubuntu  sudo apt update && sudo apt install python3 python3-venv
#   Fedora/RHEL    sudo dnf install python3 python3-pip

curl -LsSf https://hf.co/cli/install.sh | bash -s
hf auth login --token hf_xxx --add-to-git-credential   # --token is required: browser login ignores the flag
hf auth whoami                                         # confirms which account the token belongs to

It builds a virtualenv and pip-installs into it, so Debian/Ubuntu needs python3-venv as well. On macOS a good Python is often present but shadowed by an older one earlier in PATH — the installer detects that and names the directory to move up.

4 · Pre-flight — the second call is the one that matters

A read-only token passes a read check and proves nothing. Prove it can write.

# inference works and the credit is on your account
curl -s https://router.huggingface.co/v1/chat/completions \
  -H "Authorization: Bearer $(hf auth token)" -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-oss-120b:cheapest","messages":[{"role":"user","content":"say ok"}]}'

# the token can WRITE
hf buckets create <you>/preflight --private
hf buckets delete <you>/preflight --yes

Also bring git and an editor. No Docker, no Java, no Maven — the whole day is push-to-deploy, because the local stack is ~700 MB of pulls per laptop and conference wifi will not carry that for a room.

Part 2

On the day — the first fifteen minutes

Run this once, in order. Replace <you> with your username everywhere. Do not assemble it from memory — the seven APP_S3_* settings decide whether your table lands on a Hugging Face bucket or quietly falls back to a bundled MinIO, and skipping them fails silently.

# ---- 1. the code -------------------------------------------------------
git clone https://github.com/prpatel/big-data-ai big-data-ai
cd big-data-ai

# ---- 2. the Space ------------------------------------------------------
# cpu-upgrade, not the free cpu-basic: that is what the timings assume
hf repos create <you>/big-data-ai --repo-type space --sdk docker --private --flavor cpu-upgrade

# ---- 3. two buckets ----------------------------------------------------
# lakehouse: ordinary files - CSVs, catalog dump, the export
hf buckets create <you>/lakehouse --private
# warehouse: the Iceberg table, over the S3 API, NEVER mounted
hf buckets create <you>/warehouse --private
# only lakehouse is mounted, as the Space's /data
hf spaces volumes set <you>/big-data-ai -v hf://buckets/<you>/lakehouse:/data
hf spaces volumes ls <you>/big-data-ai

# ---- 4. S3 credentials: from the token, in the browser (Part 1 step 2) --

# ---- 5. settings, from a file rather than seven flags -------------------
cat > space.env <<'EOF'
APP_S3_ENDPOINT=https://s3.hf.co
APP_S3_BUCKET=<you>
APP_S3_KEY_PREFIX=warehouse
APP_S3_STS_ENABLED=false
APP_S3_CREATE_BUCKET=false
APP_S3_CLIENT_SIDE_SIGNING=true
APP_WAREHOUSE_EXPLICIT_LOCATION=false
EOF

cat space.env                  # check <you> is your username in BOTH places
hf spaces variables add <you>/big-data-ai --env-file space.env
hf spaces variables ls <you>/big-data-ai    # must list all seven

# ---- 6. the three secrets, one at a time --------------------------------
hf spaces secrets add <you>/big-data-ai -s HF_TOKEN=hf_xxx
hf spaces secrets add <you>/big-data-ai -s APP_S3_ACCESS_KEY=HFAK...
hf spaces secrets add <you>/big-data-ai -s APP_S3_SECRET_KEY=...
hf spaces secrets ls <you>/big-data-ai      # names only, never values

# ---- 7. deploy -----------------------------------------------------------
git remote add hf https://huggingface.co/spaces/<you>/big-data-ai
git push --force hf main

# ---- 8. watch it, then prove it is bucket-backed -------------------------
hf spaces logs <you>/big-data-ai --build --follow
hf spaces wait <you>/big-data-ai
hf spaces logs <you>/big-data-ai --follow   # the runtime log - keep it open all day
hf spaces logs <you>/big-data-ai | grep EMBEDDED_MINIO
Two things that trip everyone

APP_S3_BUCKET is your username, not a bucket name. LakeKeeper refuses an endpoint carrying a path, and HF buckets are addressed as namespace/bucket — so the namespace plays the part of the S3 bucket and the real bucket name becomes APP_S3_KEY_PREFIX. It reads wrongly and it is correct.

--force on the first push is expected. hf repos create initialises the Space with its own README commit, so your local main is unrelated history.

The one line that proves it worked, in the boot log: [init] EMBEDDED_MINIO=0; the warehouse lives in external storage. No such line means you are on MinIO, however healthy everything else looks.

Part 3

Load the data

At https://<you>-big-data-ai.hf.space/admin, with the runtime log still open beside you.

ButtonTakesThe log should say
Setup Environment~10sWarehouse created (or “already existed; updated”)
Download Data 2015~1mDownloaded pp-2015.csv, about 170 MB
Load Data 2015~30sData loaded successfully
The buttons lie, the log does not

All three say “… operation initiated” whether or not they worked. The log is the only place the truth is. Confirm in the SQL box on the home page:

SELECT COUNT(*) FROM lakekeeper.housing.staging_prices → about 1.01 million. If you get 0 or an error, read the log — do not just click Load again.

When stuck

Three things to check before asking

SymptomAlmost always
Setup fails with a 400 from LakeKeeperThe S3 credentials, or APP_S3_BUCKET holding a bucket name instead of your username. Re-generate the credentials and click Setup again
Generate Query returns a 500The token: either it lacks Make calls to Inference Providers, or the billing setting is wrong. The real error is in the log, never on the page
A scripted call returns 404 on a Space that works in the browserA private Space needs a session. Add -H "Authorization: Bearer $(hf auth token)"

The runtime log is the answer to most of these: hf spaces logs <you>/big-data-ai --follow. Keep it open all day.

Pair up if you can — two people per Space halves the deploy round trips, and gives one of you the log while the other writes code. A build-and-restart cycle is about 1½–2 minutes, so batch your edits and push once.
